# Gradle-native SystemUI build architecture

> **Status:** Draft for user review
> **Date:** 2026-08-21
> **Decision scope:** Release optimization, external AOSP artifact seams, SysUISdk scope,
> maintainability, and the review/migration process
> **Issue:** `docs/issues/2026-08-21-gradle-native-architecture-reset.md`

---

## 1. Decision summary

This project will build AOSP SystemUI as a maintainable standalone Android Gradle project. It
will preserve SystemUI source/resource provenance and runtime behavior, but it will not
reconstruct Soong's internal target graph, aggregated optimizer configuration, or output bytes.

The canonical strategy is **AGP-native functional parity**:

- AGP owns release code/resource optimization;
- AOSP build files are semantic and diagnostic references, not textual templates;
- non-SystemUI AOSP dependencies are packaged at the coarsest viable upstream-family seam;
- a coherent artifact may include currently unused classes/resources;
- outcomes are judged by build, package, install, launch, runtime behavior, and refresh cost;
- every consolidation or rollback is separately explained, discussed, approved, and verified.

No current artifact or SDK stage is automatically condemned by this decision. The next phase
is a read-only current-state audit against this design.

## 2. Facts about the optimization pipeline

### 2.1 Gradle is not the Android optimizer

Gradle schedules tasks and resolves dependencies. Android Gradle Plugin (AGP) assembles the
Android pipeline. For this project:

| Concern | Tool |
|---|---|
| Java/Kotlin compilation | javac / AGP built-in Kotlin |
| Android resources | AAPT2 |
| Non-minified desugaring and DEX conversion | D8 |
| Minified release code shrinking, optimization, obfuscation, and DEX output | R8 |
| Release resource shrinking | AGP 9.x optimized resource shrinking, integrated with R8 analysis |

The current release configuration enables:

```kotlin
isMinifyEnabled = true
isShrinkResources = true
```

and the actual task is `:app:minifyReleaseWithR8`. Files named `proguard*.flags` use the
ProGuard configuration language but are consumed by R8.

### 2.2 Shared optimizer does not imply shared build output

Soong and AGP may both invoke R8 while supplying different:

- program and library inputs;
- consumer rules and generated rules;
- versions and optimization defaults;
- dependency aggregation;
- resource graphs;
- DEX layout, ZIP metadata, and signatures.

Therefore neither final APK byte identity nor optimizer-configuration identity is required.
AOSP's final `proguard_configuration` is an intermediate diagnostic reference, not an input
that this project must reproduce.

### 2.3 Current Gradle release inputs

The current app release consumes:

1. AGP's `proguard-android-optimize.txt`;
2. `app/proguard.flags`;
3. `SystemUI-plugin-core/proguard.flags`;
4. consumer rules exported by Gradle dependencies;
5. rules generated by AGP from manifests, resources, and dependencies.

The audit will determine whether each project-specific rule remains necessary. It will not
add AOSP rules merely because Soong exports them.

## 3. Canonical terminology

### Functional parity

The Gradle-built SystemUI satisfies the required build and runtime behavior on its target
platform. It does not mean byte-identical output or identical optimizer decisions.

### Source alignment

AOSP SystemUI-owned source, AIDL, and resources retain the existing provenance and alignment
rules. This decision does not relax the no-stub or no-invented-resource policies.

### Artifact family

A stable upstream ownership and refresh seam such as SettingsLib, WM-Shell, WifiTrackerLib,
or iconloader. An artifact family may contain multiple Soong targets.

### Umbrella artifact

One AAR or JAR that deliberately packages the viable code/resource closure of an artifact
family. It may contain content not currently reached by SystemUI.

### Viable seam

The coarsest artifact seam that AGP can consume without duplicate classes, invalid manifests,
resource namespace/link failures, or incorrect runtime ownership. A Soong target is evidence
for a seam, not an automatic Gradle seam.

### Optimizer closure

Types and rules needed only for optimizer analysis. Optimizer closure must not automatically
be treated as APK runtime closure or used to define new artifact families.

## 4. Goals and non-goals

### 4.1 Goals

1. Build debug and optimized release APKs with standard AGP tasks.
2. Install and launch SystemUI in a compatible system image without startup crashes.
3. Preserve key SystemUI runtime behavior and platform signing requirements.
4. Keep AOSP SystemUI-owned source/AIDL/resource provenance intact.
5. Keep external dependency count and refresh seams understandable to a normal Android
   engineer using this repository as a reference.
6. Make upstream refresh family-oriented and scriptable.
7. Diagnose duplicate classes, resource collisions, reflection/JNI requirements, and runtime
   failures explicitly.
8. Keep every simplification reversible and evidence-based.

### 4.2 Non-goals

1. Byte-identical APKs, JARs, AARs, DEX files, or ZIP metadata relative to Soong.
2. A Gradle module/artifact for every Soong target.
3. Exact reproduction of Soong's merged R8 configuration.
4. Removal of every unused class/resource before AGP optimization.
5. Zero warning count as an architectural objective.
6. Immediate rollback of prior work based only on artifact count.

## 5. Module and artifact architecture

### 5.1 SystemUI-owned code

The existing source-first rule remains:

- code owned by `frameworks/base/packages/SystemUI/**` remains source;
- Gradle module seams follow real namespace, processing, AIDL, consumer, and dependency-cycle
  constraints;
- multiple internal Soong targets may share one Gradle module;
- the existing 13-module topology is retained unless a later separately approved review finds
  a concrete maintenance or correctness problem.

### 5.2 Standard third-party libraries

Use official Google Maven or Maven Central artifacts when available and compatible. Do not
repackage standard upstream libraries into local AOSP artifacts merely to resemble Soong.

### 5.3 Non-SystemUI AOSP libraries

Default policy:

1. Define one refresh seam per artifact family.
2. Package the broad viable family closure rather than the current missing-symbol slice.
3. Allow unused family-owned code/resources when they do not create conflicts or runtime risk.
4. Split only when a demonstrated technical constraint requires it.

Valid reasons to split an artifact family include:

- incompatible Android resource namespaces or generated `R` ownership;
- duplicate classes that cannot be removed without changing owner semantics;
- independently consumed interfaces with different packaging/runtime requirements;
- conflicting manifests or resource overlays;
- processing/toolchain constraints;
- a real dependency cycle.

Invalid reasons to split include:

- one Soong target exists;
- one R8 warning names one class;
- a currently unused class could be omitted;
- a smaller AAR looks more exact.

### 5.4 Target family expectations

These are audit hypotheses, not pre-approved code changes:

| Family | Desired seam | Exception threshold |
|---|---|---|
| SettingsLib | One umbrella AAR, or the smallest stable set needed for real resource namespaces | Split only with reproduced namespace/link/class conflict |
| WM-Shell | One umbrella AAR where viable | Keep a stable main/shared split only if merging causes a proven conflict |
| WifiTrackerLib | One AAR | Split only for a demonstrated independent consumer seam |
| iconloader | One AAR | Same |
| animationlib | One AAR | Same |
| Traceur/perfetto closure | One coherent artifact where viable | Separate resource/code artifact only if AGP namespace or ownership requires it |
| Build-time annotations | No runtime AAR | Use a compile/optimizer mechanism appropriate to their actual role |

The current 20 SettingsLib-family local Maven AARs are therefore an audit priority, not an
automatic rollback list.

## 6. Direct AAR and local Maven policy

The existing repository policy is reaffirmed:

1. Start with direct AAR consumption.
2. Use local Maven only when Gradle metadata and transitive resource/dependency resolution are
   demonstrably required.
3. Do not create a Maven coordinate solely for catalog uniformity.
4. A local Maven POM must describe real required dependency edges; it must not preserve fine
   Soong topology for its own sake.
5. Consolidation should remove superseded AARs, coordinates, scripts, tests, and documentation
   only after the replacement is verified and separately approved.

Artifact count is a maintainability signal, not a hard numeric limit. The deletion test is:
if removing an artifact seam merely moves the same complexity into fragile manual merging,
the seam was useful; if complexity disappears behind a coherent family packaging recipe, the
old seam was too shallow.

## 7. Release optimization policy

### 7.1 AGP-native baseline

Release keeps the standard AGP pipeline:

```kotlin
release {
    isMinifyEnabled = true
    isShrinkResources = true
    proguardFiles(getDefaultProguardFile("proguard-android-optimize.txt"), ...)
}
```

No alternative optimizer plugin is introduced. D8 remains the non-minified DEX path; R8 is
AGP's minified release optimizer.

### 7.2 Rule inclusion criteria

Additional rules are included only when justified by at least one of:

- reflection or dynamic class loading;
- JNI lookup;
- serialization/deserialization;
- plugin entry points;
- annotation processors or generated-code contracts;
- a dependency's legitimate consumer rules;
- a reproduced release-build or runtime failure.

AOSP rules may supply the solution, but their presence in Soong alone is not sufficient.
Rules are translated to the smallest Gradle-appropriate behavior; textual identity is not
required.

### 7.3 Missing-reference policy

A missing reference is classified before action:

1. **Real APK/runtime dependency** — supply a coherent program artifact.
2. **Platform runtime dependency** — expose it through the appropriate SDK/platform library
   seam without packaging it in the APK.
3. **Build/optimizer-only annotation or signature** — use the smallest maintainable compile or
   optimizer treatment.
4. **Unreachable optional path** — a narrowly scoped warning suppression may be proposed only
   with evidence that the type is not instantiated, reflected, JNI-resolved, or required on
   the supported runtime path.

A targeted suppression is not automatically forbidden. It requires documented classification,
exact scope, release build verification, and runtime validation. Broad `-dontwarn **` remains
forbidden.

### 7.4 Task 042 disposition

The prior Task 042 proposal—one SysUISdk stage plus byte-exact import of the complete AOSP
`aconfig_proguard.flags`—is rejected before implementation as over-constrained.

The remaining `AssumeTrueForR8` reference will be reconsidered during the audit as a
build/optimizer-only annotation. No replacement mechanism is chosen by this specification;
that choice must compare maintenance cost and release/runtime behavior under the policy above.

## 8. SysUISdk scope

SysUISdk remains the adapter for platform compilation/linking differences that a normal public
Android SDK cannot express:

- hidden framework APIs;
- framework AIDL declarations;
- private framework resources and IDs;
- real platform/library classes required on the target system but absent from the public SDK.

SysUISdk is not the default destination for every Soong build-time annotation or R8 diagnostic.
Every injected slice must be classified as platform-facing, prove real target availability,
and justify why a normal Gradle dependency or narrow optimizer treatment is unsuitable.

Existing stages are not removed by policy. The audit must classify each stage and each injected
slice as platform-required, optimizer-only, or obsolete, then explain consequences before any
change is proposed.

## 9. Validation model

### 9.1 Required build gates

1. Python/tooling tests relevant to changed packaging recipes.
2. `:app:checkDebugDuplicateClasses`.
3. `:app:assembleDebug`.
4. `:app:minifyReleaseWithR8` or the equivalent release optimization stage.
5. `:app:assembleRelease`, including resource shrinking and signing.
6. APK inspection for package name, manifest, signing scheme, expected native/dex/resource
   contents, and duplicate/accidental build-only classes.

### 9.2 Runtime gates

On a compatible system image/device:

1. install or place the platform-signed APK correctly;
2. launch/restart SystemUI;
3. verify no startup crash or crash loop;
4. inspect logcat for linkage, resource ID, reflection, JNI, and permission failures;
5. exercise agreed key flows such as status bar, notification shade, lock screen, QS, and
   process restart.

A build-only success is an intermediate milestone, not final functional parity.

### 9.3 Equality and determinism

Required:

- packaged classes/resources come from traceable real inputs;
- packaging scripts produce stable inventories for the same inputs;
- source extraction does not silently substitute or fabricate bytes;
- duplicate classes and unexpected resources are checked.

Not required:

- final APK/AAR/JAR hashes match Soong;
- R8 produces identical DEX structure or names;
- Gradle and Soong retain/remove exactly the same unreachable code;
- complete optimizer configuration files are byte-identical.

## 10. Upstream refresh design

A refresh should be family-oriented:

1. point tools at the new AOSP checkout/output;
2. rebuild a small set of family artifacts;
3. validate manifests, namespaces, class/resource inventories, and dependency edges;
4. run debug/release build gates;
5. run compatible device validation.

Packaging tools should expose explicit family recipes rather than per-error entry lists. Exact
allowlists remain appropriate only for security-sensitive or platform-SDK patches where
accidental expansion would be dangerous.

A successful architecture minimizes the number of independently versioned local artifacts and
the number of files touched by a normal upstream refresh.

## 11. Audit and change-control process

### 11.1 Phase 1 — Read-only present-state audit

After written-spec approval, one isolated Worker receives a read-only brief. It examines:

- current Gradle modules and dependency graph;
- current AAR/JAR/local-Maven inventory;
- current packaging scripts and rebuild seams;
- current SysUISdk stages and injected class categories;
- current release optimization rules;
- current AOSP owners and the reference project's coarse dependency approach.

It does **not** begin by mining Git history, modify files/artifacts, run rollback commands, or
make implementation commits. Its deliverable is a current-state ledger:

| Item | Present role | Real constraint solved | Maintenance cost | Design classification | Recommendation | Evidence needed |
|---|---|---|---|---|---|---|

Allowed recommendations are `keep`, `simplify`, `consolidate`, `candidate rollback`,
`needs experiment`, and `needs history/context`.

### 11.2 Phase 2 — Explanation and decision

For every non-`keep` item, the architect explains to the user:

1. why it exists;
2. what failure it originally addressed, using targeted history only if needed;
3. what guarantee it currently provides;
4. why it conflicts with or burdens the new design;
5. what a replacement or rollback would remove;
6. what build/runtime evidence would establish safety.

No change proceeds without item-specific user approval.

### 11.3 Phase 3 — Bounded implementation

Approved changes are implemented one family or mechanism at a time. Each task has its own
plan, tests, build gates, review, main verification, and rollback path. High-risk resource
families are never mixed into one batch.

## 12. Alternatives considered

### A. Strict Soong/R8 reconstruction

**Benefit:** maximum traceability to AOSP target ownership and optimizer configuration.
**Rejected as default:** creates fine artifacts and expensive refresh work without proving
better runtime behavior in the Gradle product.

### B. One opaque prebuilt containing everything

**Benefit:** few dependencies and easy initial wiring.
**Rejected:** hides provenance, risks duplicate platform/SystemUI classes, weakens source-first
rules, and makes resource/manifest ownership hard to diagnose.

### C. AGP-native functional parity with coarse family artifacts

**Selected:** preserves understandable provenance and real Android seams while allowing AGP to
remove unused content. It offers the best balance of runtime correctness, maintainability, and
reference value.

## 13. Consequences

### Positive

- Fewer independently maintained artifacts and Maven coordinates.
- Easier AOSP refresh and a more teachable reference project.
- Release rules are justified by this product's behavior rather than copied wholesale.
- Runtime validation becomes the final authority.
- Prior exactness work remains useful as provenance and diagnostic evidence.

### Costs and risks

- Umbrella artifacts may be larger before R8/resource shrinking.
- Consolidation may expose real resource namespace or manifest conflicts.
- Gradle output will diverge further from Soong internals, requiring outcome-oriented debugging.
- Runtime testing must become stronger because exact build-graph parity is no longer used as a
  proxy for correctness.

These risks are managed by one-family-at-a-time changes, explicit conflict tests, optimized
release builds, and device validation.

---

## 14. Approval and next gate

Approval of this specification authorizes only the creation and dispatch of a **read-only
current-state audit** plan. It does not authorize:

- any rollback;
- AAR/JAR/Maven removal or consolidation;
- SysUISdk stage changes;
- ProGuard/R8 rule changes;
- AGENTS.md, CHARTER, or ADR policy changes.

Every implementation decision returns to the user with its cause, history where necessary,
trade-offs, and verification plan.
