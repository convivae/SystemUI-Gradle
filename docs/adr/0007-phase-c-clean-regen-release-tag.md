# ADR 0007 — Phase C 版本固定采用「清空重生 + release tag」验收形态

日期：2026-08-26
状态：已批准（用户逐项裁决）

## 背景

Phase C（AOSP 版本固定 + 端到端可复现管线）启动前，与用户逐决策点 grilling 确认了
执行形态。此前 `libs/` 产物（jar/AAR/POM/keystore）虽已证明可由脚本再生
（task064/065/067，104 产物全部纳入脚本管线），但从未做过「删光重来」的完整闭环，
且 AOSP 树是 2026-04 的 main 漂移态，从未固定版本。

## 决策

1. **AOSP 目标版本 = release tag `android-17.0.0_r1`**（当前最新 release；main 永远
   追不上无法固定；16.0.0_r4 已过时）。固定后永久可精确复现。
2. **升级方式 = 原地切换**：现有树上 `repo init -b android-17.0.0_r1 && repo sync -d`
   （清华镜像），`out/` 全清后重建。不做双树并存（磁盘峰值不可控）。
3. **删除范围 = libs/ 全部三类**：(a) jar + aars、(b) `libs/maven/` 整棵本地 Maven 仓、
   (c) `keystore/platform.keystore`。git 历史即回滚与差异证据，不需要 fresh clone。
4. **复现成功的判定标准**：**不是**新产物与旧产物字节一致（AOSP 已漂移 4 个月，内容
   必然变化），而是——
   > libs/ 里最终入库的每一个字节都来自脚本产出，无一手工文件；
   > 且 Gradle Debug/Release 双构建 + 双 runtime 门（模拟器部署、零 FATAL、窗口在屏）通过。
5. **编译范围 = 全量 `m -j4`**：脚本消费 Soong 中间产物 + 模拟器镜像，全量是唯一
   已验证路径；精确最小目标集留作后续优化项，不阻塞本次。

## 后果

- 「可复现」的语义从「逐字节可重放」升级为「来源 100% 脚本化 + 端到端门通过」，
  这是版本升级场景下唯一诚实且可达成 的标准。
- `git diff` 在 Phase C 收尾时即是完整的产物漂移审计报告（删了什么、新生成什么、
  哪些产物内容随 AOSP 变化）。
- 签名 keystore 再生后内嵌时间戳不同 → 新 APK 签名与旧版不同，属预期；
  userdebug + test-keys 环境不受影响。
- 若 17.0.0_r1 与我们工程适配中发现不可吸收的差异（API 移除、模块结构剧变），
  回退方案是降级固定到 `android-16.0.0_r4`，成本仅为一次 sync + 重编。
