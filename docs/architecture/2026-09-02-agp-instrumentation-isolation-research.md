## 0. Executive summary

The production app-only `InstrumentationScope.ALL` `AsmClassVisitorFactory` registration fails while Gradle isolates the parameters of AGP's internal `AsmClassesTransform` (an artifact transform), and the first non-serializable object observed (Task 084, JDK extended serialization debug) is `InstrumentationContext_Decorated.__apiVersion__` (a Gradle `DefaultProperty`), reached through the runtime-generated factory decorator. AGP 9.3.1 source shows this is structural: the transform's `@Nested ListProperty<AsmClassVisitorFactory<*>>` holds decorated factory instances that AGP itself fills with non-`Serializable` Gradle `Property` objects. No reachable first-party source documents a guarantee that such a graph survives transform-parameter isolation — nor that it must not; the generic public Gradle contract for transform parameters ("managed types with managed, input-annotated properties") does not directly cover or explain AGP's nested decorated-factory graph, so no claim is made here that the graph either conforms to or exceeds that contract. The Task 086 pass (`InstrumentationParameters.None` + no-op `ALL`) and the Task 084 failure share the same decorated `__instrumentationContext__` shape, so the mechanism boundary between them is **not explained by any inspected source**; Task 087 was built to resolve exactly that variable and is **INCONCLUSIVE** because its target was UP-TO-DATE. The pre-D8 and pre-R8 position of the current ASM seam is proven from AGP 9.3.1 source (`DexingTransform`/`DexFileDependenciesTask` input selection; R8 scoped-CLASSES composition). `ScopedArtifacts.Scope.ALL` is **pre-R8-proven but pre-D8-unproven** (no dexing consumer of the scoped ALL container was found; debug dexing consumes the artifact-transform pipeline directly), so it is labeled a bounded candidate, not a recommendation. The recommended next step is a Chief-approved successor micro-control that makes `AsmClassesTransform` execution observable in the `--info` log by changing an annotated transform input in a semantically inert way; every seam decision is conditioned on that result.

## A. Official API guarantees (public, first-party)

All from the AGP 9.3.1 `gradle-api` sources artifact [S1] (canonical URL and identity in §I), streamed locally read-only.

**A1. `AsmClassVisitorFactory`** — extends `java.io.Serializable`. KDoc: "The implementation of this interface must be an abstract class where the `parameters` and `instrumentationContext` are left unimplemented. The class must have an empty constructor which will be used to construct the factory object." `parameters: Property<ParametersT>` and `instrumentationContext: InstrumentationContext` are both `@Nested`. `createClassVisitor` and `isInstrumentable` "must handle asynchronous calls".

**A2. `InstrumentationParameters`** — extends `java.io.Serializable`. KDoc: "The parameters will be instantiated using `ObjectFactory.newInstance`, configured using the given config when registering the visitor, and injected to the factory on instantiation. The parameters will be used as Gradle inputs. Make sure to declare the inputs by annotating them using Gradle's input annotations so that it's compatible with Gradle's up-to-date checks." The KDoc example annotates `@get:Input val intValue: Property<Int>` **and `@get:Internal val listOfStrings: ListProperty<String>`** — i.e. not every property must be an input, but file-bearing inputs are expected to carry input annotations. `InstrumentationParameters.None` is a static class with no members.

**A3. `InstrumentationContext`** — extends `java.io.Serializable`; `apiVersion: Property<Int>` is `@Input` and is an AGP-injected field the implementation "must leave unimplemented".

**A4. `InstrumentationScope`** — `ALL` = "Instrument the classes of the current project and its library dependencies. This can't be applied to library projects, as instrumenting library dependencies will have no effect on library consumers."

**A5. `Instrumentation.transformClassesWith` / `excludes`** — registration API as used by the production plugin; `excludes` are glob patterns over compiled class names applied to "project sources and dependencies jars".

**A6. `ScopedArtifacts` / `ScopedArtifact.CLASSES`** — `Scope.ALL` = "Full scope, including project scope, imported projects and all external dependencies"; `Scope.PROJECT` = project only. `ScopedArtifactsOperation.toTransform` KDoc: "Task will transform many inputs into a single output. That means task must have merging logic as jars contain similar files and folders (like META-INF)." `ScopedArtifact.CLASSES` KDoc directs post-compilation producers to consume `POST_COMPILATION_CLASSES` and append to `CLASSES`.

**A7. AGP 9.x API continuity** — the AGP 9.0.0 release notes [A1-REL] (fetched via `android docs fetch`) confirm `transformClassesWith` moved from `Component` to `Instrumentation` in 9.0 and remains a current, supported API; no deprecation or known-issue entry about ASM visitor serialization appears in the reachable release notes.

**What the public API does *not* guarantee:** neither [S1] nor any reachable Gradle document states that a registered `ALL`-scope factory instance will be serialized as part of a Gradle artifact transform's parameters, or that it will survive such serialization. The `Serializable` markers on A1–A3 are necessary-but-insufficient conditions; **this report does not assert Java serialization from `Serializable` inheritance alone** — the use of Java serialization at this seam is an observed runtime fact (§D1), not a documented guarantee.

## B. Source-derived facts (AGP 9.3.1 internals, first-party)

All from the AGP 9.3.1 `gradle` sources artifact [S2], streamed locally read-only. These are implementation facts of the pinned AGP 9.3.1, not API guarantees.

**B1. Registration dual-listing** (`AsmClassVisitorsFactoryRegistry.register`): an `ALL`-scope entry is added to *both* `dependenciesClassesVisitors` and `projectClassesVisitors` — an `ALL` factory is also applied to the project's own classes.

**B2. Decoration and injection** (`AsmClassVisitorFactoryEntry.configure`): the parameters object is built via `objectFactory.newInstance(paramsClass)` (or a plain `InstrumentationParameters.None()` instance for `None`), the factory via `objectFactory.newInstance(visitorFactoryClass)`, then AGP unconditionally executes `visitorFactory.parameters.setDisallowChanges(parameters)` and `visitorFactory.instrumentationContext.apiVersion.setDisallowChanges(apiVersion)`. Both injected values are Gradle-managed property instances (runtime type `org.gradle.api.internal.provider.DefaultProperty`, per the observed Task 084 stack; class identity is observational, not from these sources).

**B3. The dependency transform** (`AsmClassesTransform`): a `@CacheableTransform` `TransformAction<AsmClassesTransform.Parameters>` registered (only when `dependenciesClassesAreInstrumented`) from `CLASSES_JAR` to `ASM_INSTRUMENTED_JARS`, carrying `ATTR_ASM_TRANSFORMED_VARIANT = <component name>` plus the config's string attributes. Its `Parameters` include `@get:Nested val visitorsList: ListProperty<AsmClassVisitorFactory<*>>` — the configured, decorated factory *instances* are transform parameters, alongside `@Input framesComputationMode`, `@Input excludes`, `@CompileClasspath bootClasspath`, and a `@Internal classesHierarchyBuildService` build-service property.

**B4. Pre-D8 position (proven from source):**
- `DexingTransform` selects its input artifact type as `ASM_INSTRUMENTED_JARS` when `component.dependenciesClassesAreInstrumented` (otherwise `CLASSES`/`CLASSES_JAR`).
- `DexFileDependenciesTask` — whose `CreationAction.name = computeTaskName("desugar", "FileDependencies")`, i.e. exactly `:app:desugarDebugFileDependencies` — switches its `classes` input to `ASM_INSTRUMENTED_JARS` when `classesAreInstrumentedWithAsm`, and its output feeds `EXTERNAL_FILE_LIB_DEX_ARCHIVES` (dex archives). **The failing task of Tasks 083/084 is precisely the desugaring/dexing consumer of the ASM-transformed dependency jars.**
- `InstrumentationCreationConfigImpl.getDependenciesClassesJarsPostInstrumentation` resolves `RUNTIME_CLASSPATH` (per `ArtifactScope`) to `ASM_INSTRUMENTED_JARS` (or the fixed-frames variant) when dependencies are instrumented; `projectClassesPostInstrumentation` analogously exposes `ASM_INSTRUMENTED_PROJECT_CLASSES`/jars or, when *not* instrumented, falls back to `forScope(PROJECT).getFinalArtifacts(ScopedArtifact.CLASSES)`.

**B5. Pre-R8 position (proven from source):** `ProguardConfigurableTask` builds R8's `classes` input from `forScope(PROJECT).getFinalArtifacts(FINAL_TRANSFORMED_CLASSES)` (APK case) plus `forScope(scope).getFinalArtifacts(ScopedArtifact.CLASSES)` for each `externalInputScopes`. `TaskManager.createDependencyStreams` initializes `EXTERNAL_LIBS`/`SUB_PROJECTS` scoped `CLASSES` from `getDependenciesClassesJarsPostInstrumentation(...)` — i.e. from ASM-instrumented jars when instrumentation is active — and initializes scope `ALL` `CLASSES` as PROJECT + SUB_PROJECTS + EXTERNAL_LIBS. Hence both the current ASM seam and any scoped-artifact consumer sit **before** R8 in the graph.

**B6. compileOnly exclusion (proven from source):** every ASM-instrumented artifact path in B4/B5 is resolved from `ConsumedConfigType.RUNTIME_CLASSPATH` (`getDependenciesClassesJarsPostInstrumentation`, `DexingTransform`/`DependencyConfigurator` registration, `DexFileDependenciesTask` classes input). `compileOnly` dependencies (e.g. `framework.jar`) are not part of the runtime classpath and therefore never flow through `AsmClassesTransform`; likewise the scoped-ALL container is composed from runtime-classpath-derived scopes (B5). This is the source basis for the compileOnly-exclusion column in §E.

**B7. ScopedArtifacts mechanics** (`ScopedArtifactsImpl`): `toTransform` wires the task's inputs from the container's *current* content and republishes a single output; `toAppend` on scope `ALL` is transparently redirected to the `PROJECT` scope container; `getFinalArtifacts` is what all consumers (B5; also `BundleAllClasses`, lint inputs, `LibraryAarJarsTask`, etc. — 13 consumers identified by sweep) observe. A repository-wide sweep found **no dexing/desugaring consumer of scoped `ALL` classes**: debug-build dexing consumes `ASM_INSTRUMENTED_JARS`/`CLASSES_JAR` via the artifact-transform pipeline and internal dex-archive artifacts, not the scoped-ALL container.

## D. Interpretation (inference — clearly separated from A/B)

**D1. What is actually observed vs guaranteed.** Task 084's JDK-extended stacktrace is direct runtime evidence that *Java serialization was used* at the moment the parameters of `AsmClassesTransform` were handled for `:app:desugarDebugFileDependencies`, and that the first object rejected was `InstrumentationContext_Decorated.__apiVersion__` reached via `AconfigReferenceRewriteFactory_Decorated.__instrumentationContext__`. Nothing in the inspected public docs (Gradle userguide artifact-transforms page [G1], `TransformParameters` Javadoc [G2]) promises or forbids this: the *documented* parameter contract is "managed types, managed properties, input-annotated getters". AGP holding decorated factory instances (with injected `DefaultProperty`s) in a `@Nested ListProperty` of a cacheable transform is an **AGP-internal shape that is not directly covered or explained by that generic documented contract** — this report deliberately makes no stronger claim in either direction (neither that the shape "exceeds" the contract nor that it is sanctioned by it). Consequently the honest classification of "bug vs unsupported shape" is: **undocumented territory — neither a confirmed AGP bug (no reachable tracker issue; none found in release notes) nor a documented-supported shape.** No fix or regression reference could be confirmed from reachable first-party sources (§H gap).

**D2. The 084-fail / 086-pass asymmetry is not explained by inspected source.** Both runs register an `ALL`-scope factory through the same `AsmClassVisitorFactoryEntry.configure` path (B2), so both decorated factories carry the identical `__instrumentationContext__.__apiVersion__` shape that failed in 084 — yet Task 086 (`None` + no-op) completed `:app:desugarDebugFileDependencies` successfully. Candidate hypotheses (unproven): (H1) Gradle's parameter isolation takes a different path (or short-circuits) for the `None` parameter value; (H2) the transform executions in 086 were satisfied without the isolation step that failed in 084 (the task-level log "3 executed, 2 up-to-date" counts tasks only, not artifact transforms — [G1] documents transforms "will not be rerun if possible" with cache reuse); (H3) the trigger is some interaction of the production factory's specifics rather than the parameter type. None of these can be confirmed statically; this is precisely the variable Task 087 isolates.

**D3. Why Task 087 is INCONCLUSIVE.** Task 087's target was UP-TO-DATE. Because the AsmClassesTransform is an artifact transform (not a task), the task-level UP-TO-DATE marker proves neither that the transform re-executed (and hence passed isolation) nor that it was skipped/reused. Two readings: (a) the transform was satisfied from cache without re-execution → no signal about the custom parameter shape; (b) the transform re-executed and succeeded, producing byte-identical no-op jars, leaving the desugar task's input fingerprints unchanged → UP-TO-DATE would then actually imply a *pass* for the custom-params shape. The log captured for 087 does not distinguish (a) from (b). Treating it as no-signal (INCONCLUSIVE) is the conservative and mandated reading.

**D4. The `fileValue(File)` question.** `RegularFileProperty.fileValue(File)` is a public Gradle API for setting a concrete file value; nothing inspected forbids it inside `InstrumentationParameters`. The production parameters interface itself (`AconfigReferenceRewriteParameters`, `@InputFile @PathSensitive(RELATIVE)`) matches the documented input-annotation discipline (§A2). Given D2/D3, there is **no first-party basis to conclude the file-backed parameter shape is the isolation blocker** — that conclusion is exactly what a properly-executed Task 087 would test. Note that Task 084's failing field is *not* one of the two file properties; it is AGP's own `__apiVersion__`.

## G. Recommended next step (single, smallest)

**Run a Chief-approved successor micro-control whose purpose is to make `AsmClassesTransform` execution — or its failure — observable in the log, rather than re-running 087 verbatim and relying on the ambiguous task-level marker (§D3).** The design problem the micro-control must solve: neither `--rerun-tasks` (documented only for task up-to-date forcing, [G3]) nor `--no-build-cache` (documented to disable the build cache) is **proven, from any inspected first-party source, to force re-execution of artifact transforms**; passing either or both flags alone therefore cannot establish that the transform actually ran. The candidate mechanism, subject to Chief approval before any implementation: extend the no-op factory's parameters with an additional annotated transform input (e.g. a temporary copied file input whose content/path is changed for the run, if separately authorized) so that the transform's input fingerprint demonstrably changes in a semantically inert way — the factory itself remains a no-op and the four mappings/166 allowlist remain untouched. Run `:app:desugarDebugFileDependencies` once with `--info` captured, so the log shows the `AsmClassesTransform` executions (or their absence/serialization failure) for the file-dependency jars. The exact parameter design, file location, and command are the Chief's call (the 087 brief pins its command; a successor micro-task brief is the cleanest vehicle). No seam change should be made before this result exists: the decision table in §F shows every branch depends on it, and the two viable fallback seams each carry an unverified coverage precondition (PROJECT-scope: durable census plus demonstrated project-instrumentation execution; ScopedArtifacts: pre-D8 timing).

## H. Unresolved questions / research gaps

1. **AGP issue tracker** (`issuetracker.google.com`) was not consulted this pass (bounded budget; googlesource/developer.android.com fetches were unreachable earlier). Whether the `AsmClassesTransform` params-serialization failure is a *known* AGP bug with a fix version remains open — the honest verdict stays "undocumented shape" (D1) until the tracker is checked.
2. **First-party AGP tests** for `AsmClassesTransform` (on googlesource) remain unread; no confirmed first-party example of `ALL` + file-backed parameters exists in the evidence set (§C).
3. **Gradle's exact isolation mechanism source** (where transform parameters are Java-serialized) was not located — GitHub code search requires auth; the mechanism is cited only as observed runtime behavior (Task 084), never as a documented guarantee.
4. **Whether `--rerun-tasks` or `--no-build-cache` re-runs artifact transforms** is not established by [G1]/[G3] for either flag; G's recommendation therefore rests on changing an annotated transform input (fingerprint-level proof of re-execution) plus `--info` log-level evidence, not on any flag alone.
5. **`FINAL_TRANSFORMED_CLASSES` republish chain** (APK project scope into R8) was seen referenced (B5) but its producer call site was not traced — matters only if ScopedArtifacts is pursued.
6. **Durable census of the 166 allowlisted classes** (project classes vs external jars) was out of scope for this report but is the coverage precondition for the PROJECT-scope fallback (§E) — and by itself is still insufficient: actual project-instrumentation execution under PROJECT scope must also be demonstrated (no observed failure on that path is not proof of success).
7. **D2's mechanism hypotheses** (H1–H3) are unproven; only a properly-executed successor control making `AsmClassesTransform` execution observable (G) can discriminate.
